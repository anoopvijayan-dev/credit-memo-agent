(iv) Wait for the lock before reading: lost in revision 5. *Chose (iii)*, the owner's take-over. It needs no writer state: the operating system's locks say everything, and the lock files hold no data. What (iii) costs: a second lock file in every case folder; a writer waits at the gate while checks hold it, up to a set time, so a check run in a tight loop can hold off a save until it is refused; and a writer paused while it holds the gate has not taken the case, so a check that finds the gate busy tries the case lock directly and reads holding it if it is free (D98, after verify-52). If the case is held as well, the check does not hold the gate, and the next sub-decision says what it may report.\n\n**Sub-decision: a writer at the gate while another holds the case (revision 11, after verify-54 and verify-55; owner question).** A check that finds the gate busy tries the case lock directly (D98). If the case lock is held too, the check does not hold the gate, so it cannot know that one writer held the case through its read. The holder can let go, leaving an incomplete entry, and the writer at the gate can take the case between the check's two looks. That is verify-47's corner, which the gate closes only for a check that holds it. (i) From a steady read, name a change, removal or reordering at or before the recorded entries, which is wrong whoever holds the case. Write into R43 and P15 that a steady read gives the recorded entries only when one writer held the case through it. (ii) From a steady read, report the recorded entries and the rest as being saved, as verify-55 reads R43 today; no requirement change. (iii) Wait at the gate for the writer passing it before reading. *Chose (i)* as the design default. (ii) lost because it reopens verify-47's corner. (i) Detect and refuse every interference, by joining the check of the lock file to each write: no file system offers that as one step, so a window remains between the check and the write, and each review would find it again. (ii) State it: the gate and the case lock are the tool's own files; removing or replacing them while the case is in use is outside R42's guarantee, as hand-editing the log is. A writer re-checks its lock before each write and refuses if the file was removed or replaced, and if such interference still lets two writers append, the log they leave is reported broken, never intact. (iii) Lock the log file itself, so that removing the lock removes the log: the repair replaces the log by rename, which would hand its lock to nobody, and a reader's gate would still need its own file. *Chose (ii)*, the owner's answer (D99). Two appends at one position leave two entries that claim it, so the chain or the head record fails there whatever order their writes take. What (ii) gives up: a cleanup script, a sync or backup client restoring a folder, or a person deleting the lock files can let two writers append; the log is then reported broken, and the second save is redone after the log is repaired. A repair is covered only by the sub-decision after next.\n\n**Sub-decision: which steps a writer re-checks its lock before (revision 11, after verify-54 and verify-55; owner question).** R42 says a writer re-checks its lock before each write. An append changes the case's files in up to three steps: the empty head record before the first line, the line, and the rename that publishes the new head record. A repair has two: the rename of the rewritten log over the old one, and the rename of the head record. Each rename is prepared in a temporary file that nobody reads. (i) Before each step that changes a file a reader reads: the empty head record, the line and each rename; writing a temporary file is not such a step. (ii) Before each append and each repair, as revision 10's C3 said, and amend R42 to say so. (iii) Make the check and the step one: no file system offers it (revision 10). *Chose (i)* as the design default. It is what R42's words say and what verify-55 asks, and each check is one file status call. It leaves only the window between a check and the step itself, which revision 10 states. (ii) lost because it keeps a wider window than R42's text allows, so R42 would have to change for a weaker guarantee. What (i) costs: a step refused after the line and before the head record leaves the entry past the recorded entries, as a crash does. The writer says the save was not recorded, and the next holder confirms dropping it.\n\n**Sub-decision: a repair under such interference (revision 10; D103).** Dropping a torn entry rewrites the log through a temporary file and a rename, so that a crash leaves the old log or the repaired one. Suppose interference lets a second writer take the case, drop the same torn entry and append, all between the first writer's re-check and its rename. The rename then removes the second writer's entries, and the first writer's head record matches what is left, so the log reads intact. (i) State it: under such interference a repair can remove another writer's entries without a break, as a hand edit of the log and its head record together can; the files cannot show it, and a signed pack pins the head it saw. (ii) Make the repair an append: the torn bytes stay, ended by a newline, followed by a drop entry that names them, and a reader skips a line only when the entry after it names it. Every write is then an append, so D99's 'broken, never intact' covers repairs too. *Chose (i)*, the owner's answer (D103), as D63 and D66 kept to stating a scope. (ii) lost for now because it changes the log format and the reader in a task that has used its attempts, for a case that needs both interference and a torn entry. What (i) costs: D99's guarantee holds for appends; a repair under interference can lose another writer's save silently until a signed pack is compared.\n\n## Decision\n\nBuild Option A as components inside the existing package. The gate and the case lock sit beside the log and hold no data. Before each step that changes a file a reader reads, a writer re-checks that the case lock file is still the one it locked (revision 11; owner question). Those steps are the empty head record that precedes the first line, the line, and each rename that publishes a head record or a repaired log. Refused after the line, it leaves the entry past the recorded entries, as a crash leaves it, says the save was not recorded, and the next holder confirms dropping it. Someone who removes or replaces a lock file while a writer is between its check and its step can let a second writer take the case and append too. That is outside R42's guarantee, as hand-editing the log is (D99). A reader while another writer holds the case reports being saved for what follows the recorded entries. An ambiguous credit holds `<ruleset>:conflict:` followed by every table candidate rule id in table order, then, since revision 7, `profile:director` and `profile:own_account` for each kind of profile name its wording matches, in that order, all joined by +; its category is other (unexplained). Since revision 4 the table candidates are every rule the credit matched in either stage, payment-method cues included, after a match inside a longer listed phrase counts as the longer one; since revision 5 a phrase that starts inside another match of the same rule is found too; since revision 6 a cheque is a payment-method cue and a listed name is found whatever separators stand between its letters. Thresholds live in a packaged, validated YAML file that the firm can replace. Amounts in it are pounds with at most two decimals and are compared in pence. While a threshold still has its shipped value, the workspace and the pack call it illustrative, as they do the policy. Kinds: a large single credit against typical trading receipts; a cash deposit at or above the single-deposit limit; a month with cash above a set share of its trading receipts; cash paid in within a window of days after a cash withdrawal, the two amounts within a tolerance; a payment to a gambling operator; a returned direct debit; a run of consecutive overdrawn days; an irregular credit from a named acquirer, read from the acquirer and gateway name lists whatever category the line took. Shipped cash values: a single deposit of £2,500 or more and cash above 50% of a month's trading receipts (D35), and a round trip within 7 days and 10% of the amount (design default). An ambiguous credit is not categorised as cash, so the cash indicators do not read it; it is in the judgement queue as unexplained.\n\n**Policy check.** PolicyResult and policy.evaluate do not change. Protected in v2: the line-type cues, and lender, director, capital-introduced, shareholder and generic loan and advance wording. Each table has an id and a hash. It writes nothing.\n- `cma case sign CASE` asks for a typed name, checks the snapshot against the preview and writes the pack once. It is interactive only; there is no --yes. Output: the five-column statement for one account, the account metadata, and an optional hints file. The output must pass ingest.load_csv unchanged, and all importers share one step that walks and verifies the balance. Refusals give line or record numbers, never cell values, as the MCP server does today.\n\n**Case log contract** (revisions 5 to 11; internal to the package, with the writers listed in Consumer trace item 20).\n- A writer passes the gate alone and briefly to take the case, then holds the case lock alone, and states the log position it last saw. It waits while checks hold the gate or the case, waits a moment for another writer and is then refused, and gets a conflict if its position is stale. The first append writes the head record before its line.\n- Before each step that changes a file a reader reads (the empty head record, the line, each rename that publishes a head record or a repaired log), a writer re-checks that the case lock file is the one it locked. It refuses the step if the file was removed or replaced; refused after the line, it leaves the entry unrecorded and says so (revisions 10 and 11).\n- A check is not a writer: it holds the gate shared while it reads, and the case lock shared when the case is free, on every platform, so checks never exclude each other.\n- A reader gets one of five answers:\n  1. the whole log intact, with its head and entries, only from a reader that holds the case or found it free;\n  2. the first bad or incomplete entry with its reason;\n  3. the case being saved, with the recorded entries it judged and the rest not yet checked, only while one writer held the case throughout the read, which the gate ensures, and still holds it after;\n  4. the case being saved with nothing claimed, when that writer gave no steady read, or when every attempt found a writer at the gate and the case held and no steady read showed a fault at or before the recorded entries, which answer 2 would name;\n  5. when the lock cannot be taken or tested and no read held still, not checked, with the lock error named and nothing claimed.\n- Whatever needs the whole log intact (an append, a sign-off) decides holding the case, and no caller presents being saved or not checked as intact or as broken.\n- Messages name entries by number and never quote their content.\n- No caller forks while it holds the lock, every caller keeps case folders on a local disk, and no caller removes, replaces or moves the gate or the case lock while the case is in use. Interference with them is outside the single-writer guarantee; two appends that it lets through leave a log that answer 2 names, never answer 1 (D99).\n\n**Review workspace API.** Internal to the package; the page and the server ship together, so it is not a shared contract. A line in the judgement queue carries its rule and, for an ambiguous credit, its candidates, each with the category its rule or profile kind sets and the bucket that category maps to, or no bucket for a payment-method cue (R15). A line in a drill-down carries its rule as recorded (R16). The firm-rule preview counts the lines the rule matches and will not apply to, because a protected or ambiguous verdict, or a profile name, settled them (R20, R21, R4). The workspace listens only on loopback, requires a random per-launch token on every request, rejects any Host header that is not the loopback address (against DNS rebinding) and sends no permissive CORS headers. Writes also need the expected log position.\n- **The lock files are not access control** (revisions 5 and 10). The gate and the case lock order honest writers on one machine; access is the case root's owner-only permissions (R31), which `cma case check` relies on rather than checks. Someone with the operating-system user's rights can delete the lock files. A writer then refuses once it sees its file gone or replaced, and two appends that still get through show as a broken log. Such a person can also rewrite the log and its head record together, which the files alone cannot show; a repair under lock-file interference can do the same to another writer's save. The sign-off and the pack pin the log head they saw (R22), so a later rewrite no longer matches a signed pack. A writer that keeps saving can keep other readers at being saved, but cannot make them report the log as intact or broken (revision 6); sign-off and every append judge the whole log while holding the case. A process that checks a case in a tight loop can make another window's save wait at the gate and then be refused (revisions 7 and 10); that takes the same user's rights, which already allow worse.\n- **Trust boundary:** bank data the applicant controls enters through the importers, and the loader checks its structure and balance chain. Descriptions are written by payers: they are escaped in HTML under a strict content security policy with no inline script, formula characters are neutralised in CSV, and they never go into prompts. The candidate rule ids shown for an ambiguous credit, and their buckets, come from the shipped tables and the two fixed profile kinds, not from payer text. Which wording is the bank's own code is listed in code, so neither a payer nor a table edit can claim it (D97). Case-log messages name entries by number and never quote their content.\n- **Secrets:** an optional model API key in the environment, only when the offline lock is off. It is never logged or written to evidence.\n- **Personal data:** statements, the profile (director names, account identifiers), override reasons and packs stay in the case folder. Evidence holds ids, figures, rule ids and hashes, not descriptions or the profile; a profile candidate is recorded by its kind, never the name. Purge deletes the folder and leaves a ledger line with no personal data. Encryption at rest is the firm's disk encryption; the tool adds none of its own. Retention follows the firm's policy, and purge is how the tool carries it out.\n- **Risk path:** lending data (risk: data). The human acknowledgement is the named sign-off bound to the snapshot. The name is typed, not authenticated (README known limit), so the OS user is recorded alongside it. Real sign-in belongs to a hosted version. The illustrative outcome is computed, labelled and never signed as a decision.\n- **Worst cases with this deployed:**\n  1. An applicant writes script into a payment reference to act in the underwriter's browser, for example to change categories or sign off. Escaping, the content security policy and the token stop it.\n  2. An applicant makes money look like trading income: by naming the payer after an acquirer, adding an invoice reference, or, since D31, paying cash in.\n     - The round-trip check, the director-name rule and the indicators surface it, including the three cash indicators, and the line is one click from its figure. Cash split below every limit is the gap that remains, and it is visible only in M18.\n     - Since D52, wording that mixes lists cannot reach trading receipts: a payer who adds a second list's word only sends the credit to the queue. Every line-type cue is non-trading, so payer-written cues can lower M2 but never raise it.\n     - Since revision 4, a listed name hidden inside a longer word in any alphabet does not match, and since revision 5 that holds after a combining mark too. Adding a gateway's name to an invoice-referenced credit does not take it out of the round-trip check.\n     - Since revision 6, a typographic dash, a dot or an invisible character can no longer hide a payment-method cue or a lender phrase, and a cheque cannot hide cash wording. A payer can still split a short trading name across words to be read as it (E BAY), which counts as trading receipts as the plain spelling always did; the irregular-acquirer indicator reads it.\n     - Since revision 7, a payer cannot take an ambiguous credit out of the queue by naming a director or an own account in the reference: the name adds a candidate and settles nothing. A payer can still name a director in the reference of a credit the table does not find ambiguous and no protected verdict decides, which moves it to director funding (R5); that lowers M2, never raises it.\n     - Since revision 8 the requirements say what the build already did: a profile name in a refund, a loan or a returned payment cannot move it out of its protected verdict, and both readings are non-trading.\n     - Since revision 9, a payer who writes both a director's and an own account's names into a reference only sends the credit to the queue, which lowers M2, never raises it.\n     - Since revision 10, a payer cannot write wording that passes for the bank's own returned-payment code, which only a code listed in the program at the start of the line can be.\n  3. Someone turns the offline lock off and uses a hosted model. The prompt still carries only tables (P5), and the evidence records where data went.\n  4. Someone with the underwriter's login edits the case log and its head record together, or deletes the lock files and repairs the log while another window saves, to hide an override. The files cannot show it, but a signed pack pins the head it saw, so the edit shows against every signed pack.\n- **Pseudonymised is not anonymous:** amounts, dates and balances can identify a business again, so the output is labelled as personal data.\n\n## Consumer trace\n\nThese are the shared contracts this change touches, with every consumer found.\n\nWhere each item was searched:\n- Items 1-10 were searched with ripgrep from the repository root at e618469 for revision 1, and their cited lines were re-read at 43f3e57 for revision 2.
