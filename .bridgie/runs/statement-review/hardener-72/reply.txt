I checked the T34 change against every checklist and wrote `claim.json` to the run folder. The full suite passes (2722 tests) and lint is clean; my three file changes are left uncommitted in the worktree.

**What I added:**
- **A stale-sign-off test** in `tests/test_signoff.py`: if the pairing days change after a preview, sign-off refuses that preview, naming "the own-account pairing days", and writes nothing.
- **Two tests** in `tests/test_own_account_pairing.py`:
  - Deleting the `firm.yaml` key brings back the 3-day default with no repair.
  - A bad value refuses the workspace figures, naming the key, rather than falling back to the default quietly.
- **README:** what the `own_account_pairing_days` setting does (default 3, range 0 to 31), that it is bound into the preview, and a rollback step.

**Gaps for the owner** (in `notes`, not changed in code):
- **Rollback hazard:** an older release refuses a `firm.yaml` with a key it doesn't know. So a firm that sets this key and reinstalls an older version has its whole `firm.yaml` refused, the offline lock included. That fails safe, and deleting the key fixes it. The README now says so, but the design's rollback section doesn't yet.
- **Single-account cases:** changing the setting also makes a single-account preview stale, although pairing never runs there. That is cautious and costs one more preview.
- **Design doc:** `design.md` doesn't mention the new `firm.yaml` key yet. A design revision should add it.
- **No case-log entry:** changing the days changes an open multi-account case's figures in the workspace without anything recorded in the case log. The only guard is the preview check at sign-off, as for `show_policy_verdict`.
- **No alert:** the design has no remote alerting by choice, so the tool refusing is the only failure signal.
