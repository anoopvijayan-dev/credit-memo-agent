My verdict on T15 is **pass**: R35 is met and I found no blocker or major issues, only three minor ones. Writing `evidence.json` into the run directory was denied, so the evidence is the JSON block at the end of this reply.

**R35 holds.**
- **Deletion:** every file a case has lives under `cases/<id>/`. The purge takes the case as a writer, renames the folder out of use while holding it, and deletes everything, including the read-only input files.
- **Ledger:** the line holds only the case id, the UTC time and the operating-system user. It is written under a lock that also stops a case being recorded twice.
- **Caller:** production code calls the purge through the new `cma case purge` command.
- **Tests:** the runner's logs show all 13 tests in `tests/test_case_purge.py` ran and passed. That includes the test that no file named by the case is left and that the ledger has no personal data.

**Minor findings:**
1. **A waiting save can recreate the folder** (`src/cma/case.py:842`). A profile change or import that is waiting for the case during a purge still creates the folder and lock files once it gets the lock. It then fails, so no statement or profile data comes back. But an empty `cases/<id>/` with two lock files is left after the ledger says the case was purged, and purging again answers "no case", so it cannot be cleaned up. The hardener fixed the same problem for a second purge but not for other saves.
2. **A cut-off ledger write breaks the next line** (`src/cma/store.py:666`). If a ledger append is cut off, the next purge's line is joined onto the fragment. The duplicate check then can't read it and can record that case twice. The code also doesn't check for a short write.
3. **The claim is stale.** Its note (1) says a lock on the ledger is still needed, but the final commit adds it. It also cites 12 tests where there are now 13.
