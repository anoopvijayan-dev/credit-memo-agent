**Major: the nested-save guard still misses a case whose folder does not exist yet.** R42 requires a save begun inside another save on the same thread to be refused before it writes anything, and revision 23 keeps that rule even under interference.
- `_one_save` (`case.py:961`) works out its key before `writer()` creates the folder (`mkdir` at `:842`). With no folder, the outer save's key falls back to the resolved path.
- A nested save from a handler (for example via `_utc_now` inside `_encode` at `:1122`) runs after the folder exists, so it gets the device-and-inode key. The two keys differ and the guard lets it through.
- The writer lock admits the same thread, so the nested save writes the head, its line and the head record, and is told it was recorded at entry 1.
- The outer save then fails with a `LogConflict` at `:1201`.
- The existing test only covers a folder that already exists.
- To reproduce: point `CaseLog` at `tmp/new/log.jsonl` with `tmp/new` absent. Patch `case._utc_now` to start one nested `append(expected=0)` on a second `CaseLog` for the same path. Call `append(expected=0)`. The nested append returns an entry instead of raising "under way".

**Minor findings:**
- **Head-file check uses the inode number:** `_file_identity` (`case.py:251`) relies on device, inode, size, mtime and ctime. A take-back's staging file can reuse the inode number freed by the publish, and within one timestamp tick all five values can match. A steady read would then still hide a publish followed by a take-back, though this is unlikely.
- **Claim 3 is wrong:** it says that while another command holds the lock, the check exits 0 with "appending". The test (`test_case_log.py`, around line 1060) asserts exit 4 and "being saved".
- **Claim 6 is stale:** it says `case.py` has 559 insertions; the diff adds 1518 lines.
