**What passes:**
- Only booked lines are kept, and pending ones are counted.
- Only GBP is accepted, and nothing is converted.
- The bank's `TransactionId` is kept as the line id.
- A transaction repeated across pages is kept once when identical, and the file is refused when the two copies differ.
- All the `test_import_openbanking` tests ran and passed in the runner's contracts tier (contracts-4.log:171-222).
- The previous review's finding is fixed: the 8/12/400 balance-less-line tests pass.

**The new defect (major):**
- **Where:** `_first_order` (`openbanking.py:510-527`) is used when nothing before the first balanced group says what the balance is. To test a guessed starting balance, it orders each later group that has a balance. But `_order` hands back any single-line group unchecked (`openbanking.py:295`).
- **Effect:** when later groups are single lines (any export where the other lines have their own timestamps), the first guess, "the balanced line goes first", is accepted. The walk then hits a later per-line balance it doesn't match, and a valid file is refused as a broken balance chain. That is the refusal R36 allows only when the chain really breaks.
- **Repro:** opening balance £100.00.
  - L0: credit £5.00, no balance, 2026-05-01T00:00Z.
  - A: credit £1.00, balance £106.00, same moment.
  - B: credit £1.00, balance £107.00, 2026-05-02T00:00Z.
  - The order L0, A, B chains correctly. The importer picks A, L0 instead, walks B to £112.00 against the file's £107.00, and refuses it.
- No test covers this shape: every test either has a balanced line before the mixed group or has multi-line later groups.

**Smaller findings (minor):**
- The search can still refuse valid files, now with a "search limit" message. This happens when the first balanced group has more than 16 lines without a balance and needs an unusual subset of them first, or when there are more than 32 distinct amounts among them. The README and the heavy-mix test both accept this.
- `claim.json` doesn't match the code under review. It says `ORDER_STEPS` is 100,000 (the code has 500,000), and that the distinct-amounts test is a strict xfail (no xfail is in the file; the runner ran it and it passed). It also reports "52 passed, 1 xfailed", which no runner log shows, and its proofs ran from `/tmp` scripts the runner didn't run.
