**Verdict: fail.** The promotion works when one case writes at a time, but two cases promoting at the same moment can lose one firm rule while both case logs record it as saved. That breaks R20's "save … to the firm rules file".

I read the repository, not just the packet. The runner's specified and contracts logs show the promotion tests ran and passed (24 PASSED lines in each).

**R20 — fail.**
- What works:
  - The preview lists the lines the rule matches and writes nothing (`promotion.py` `preview`/`_build`).
  - Saving rebuilds the preview while holding the case. It refuses if the line count or the digest has changed, then writes the pattern, direction, category, name, UTC time and reason (lines 281–313).
  - The open case and later cases pick the rule up, because `overrides._categorise` re-reads the rules file each time and its cache key includes the file's hash.
  - The tests for "the preview count matches" and "later cases apply the rule" ran and passed.
- What fails: the firm rules file is shared by every case, but `promote()` locks only the open case. Its "has the file changed?" check at line 303 comes before the write at 308–309. Two cases can both pass that check, and the second write then silently drops the first case's rule (major). The producer raised this in their notes and left it as a design decision. Under the review rules it still counts against R20.

**R42 — pass.** The promotion goes into the case log as a `firm_rule_promotion` entry through `store._recorded`, carrying the previous entry's hash. The rules file is put back if the entry isn't recorded, and the test for that ran and passed.

**Findings**
1. **Major — lost rule under concurrent promotion** (`src/cma/promotion.py:303`). Two workspaces on two cases sharing one rules file:
   1. Both read and build their preview.
   2. Both pass the check at line 303.
   3. Case A writes A's rule; case B then writes B's rule over it, without A's.
   4. Both case logs record a promotion, but A's rule is gone.
2. **Minor — rollback can delete another case's rule** (`src/cma/promotion.py:308`). The undo saves the file as it was before this case's write. If case B writes after case A, and A's case-log entry then fails, A's undo restores the old file. B's rule is deleted although B's log records the promotion.
3. **Minor — the preview's "would set it" column can be wrong** (`src/cma/promotion.py:214`). The column is worked out line by line. It misses effects across the whole statement, such as own-account pairing. Example: in a two-account case, a credit "FPS CREDIT ACME TRUST" is paired as an own-account transfer, and another ACME TRUST credit is overridden to `returned_dd` and promoted. The preview says the pairing settles the first credit, so the rule won't set it. After saving, the rule makes that credit a returned payment, which can't be paired, so the pair breaks and the rule does set it. Its debit partner also changes category without appearing in the preview. The line count is still right; only the per-line answer is wrong.
