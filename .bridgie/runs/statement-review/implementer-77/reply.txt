**How promotion works from the workspace:**
- **Where to start:** the case page lists each override the case applies, with a form to type a counterparty pattern and pick a direction. The direction defaults to the line's own: a credit gives "in", a debit gives "out".
- **Preview first:** submitting the form only shows a preview and saves nothing. The preview lists every line in the open case the rule would match and how many of them the rule would recategorise. For each line the rule would not change, it says what keeps it:
  - an override
  - an own-account pairing
  - a protected built-in pattern such as HMRC (R21)
  - ambiguous wording
  - a profile name
  - an earlier firm rule
- **Saving:** confirming adds the rule to the firm rules file with the pattern, direction, category, typed name, UTC time and reason. It also logs a `firm_rule_promotion` entry in the case log.
- **What the log entry holds:** the rule id, direction, category, which override it came from, the counts shown, who promoted it and when, and the hash of the new rules file. It leaves out the pattern and the reason, because they are text about the applicant's counterparties.
- **When nothing is saved:** in each of these cases no rule is saved and the rules file is left as it was:
  - the number of matching lines has changed since the preview
  - the page is out of date (another save happened since)
  - the case log refuses the entry
- **Later cases:** every case reads the rules file as it stands, so the open case and any case categorised afterwards apply the rule.

**Limits:**
- Saving rewrites the firm rules file from its checked contents, so any comments someone typed into it by hand are lost.
- The rules file is shared by every case. Two promotions saved from two different cases at the same moment are guarded only by a check just before writing, not by a lock.
- There is no `cma case promote` command, because the task asks only for the workspace.
- A pack preview built before a promotion will be refused at sign-off as out of date, because the rules file's hash is part of what is signed. That is the existing sign-off behaviour.
