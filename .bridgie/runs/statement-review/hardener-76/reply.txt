The fix for the review's finding (a promotion could lose another case's rule) holds. Promotions from two cases now take turns on a lock beside the shared firm rules file. I added two tests that prove it across processes, and the whole suite passes (2,889 tests). I changed no production code. Five checklist lines are gaps for you, listed in `notes`.

**The finding.** Two cases promoting at once no longer lose a rule. While one promotion is saving, the other waits, and both rules end up in the file. If a promotion's case log refuses it, putting the file back never removes another case's rule that was already recorded. The two thread tests that came with the fix pass. The lock is `flock`, which also shuts out other processes, so I added:
- a test where a separate process tries to take the lock while a promotion holds it, and is refused; it takes it once the lock is released;
- a test where a promotion can't get the lock within its wait. It is refused with "another case is saving a firm rule", and neither the firm rules file nor the case log changes.

**Other checklist lines with proof:**
- **Who can call it:** a request with no token, a wrong token, another site's Origin, or a GET is refused, and nothing is saved.
- **Idempotency:** sending the same confirmed promotion twice saves one rule and one case log entry.
- **Rollback of a refused save:** if the case log does not record the promotion, the firm rules file is put back as it was.
- **Stale previews:** a promotion is refused if the preview now counts different lines, gives a different result, or the case moved on since the page was built.
- **Input:** the pattern is matched as a name, never as a regular expression. A malformed firm rules file is refused and left untouched.
- **Personal data:** the case log entry holds neither the pattern nor the reason. The rules file is readable by its owner only.
- **Escaping:** case text in the preview page is escaped.

**Gaps in `notes`:**
- **Lock on Windows:** the Windows lock path is not exercised. CI runs Linux only; the plan was always to run it once on a Windows machine before the demo.
- **Lock path:** the lock's location is worked out from `firm.yaml` before the lock is taken, and `firm.yaml` is read again inside it. If the rules file's location changed in that moment, the lock would sit beside the wrong file. This is an edge case and needs your call.
- **Timing:** the preview categorises the case twice, and saving holds the firm-wide lock while it does. No test times this against the 2-second target at 10,000 lines.
- **Signals:** apart from the case log entry, nothing records or alerts on a promotion that times out on the lock. This tool has no remote alerting by design.
- **Docs:** the README doesn't mention the new lock file beside `firm_rules.yaml`. That is a docs change for you.
